# Load test, 2026-11-10

Run with k6 0.55.0 against a local production build (`pnpm build`, `pnpm start`)
on the production database. One Node process, no CDN, no edge cache.

## Command

```bash
BASE=http://localhost:3000 k6 run ops/load.js
```

`ops/load.js` reads only: home, city, dish, place and search. It never submits,
reports or geocodes, so a run costs nothing on the paid or rate-limited endpoints.

## Profile

10 virtual users ramping up over 30 s, held for 60 s, ramped down over 15 s.
Path chosen at random from the five above, so the mix ≈ 3 page reads per search.

## Result

| Metric                   | Value                                    |
| ------------------------ | ---------------------------------------- |
| Iterations               | 1163 in 1 m 46 s (11.0/s)                |
| Checks passed            | 2326/2326 (100%)                         |
| `http_req_failed`        | 0.00%                                    |
| `http_req_duration` p50  | 265 ms                                   |
| `http_req_duration` p95  | **2.25 s** (budget 800 ms, **breached**) |
| `http_req_waiting` p95   | 247 ms                                   |
| `http_req_receiving` p95 | 2.02 s                                   |

## Reading it

Time to first byte stays flat at ~247 ms while body transfer grows to 2 s, so the
server is CPU-saturated rendering and streaming, not waiting on the database.
`/search` is the slow payload in the mix (1.36 s alone, see `docs/slo.md`).

Two consequences:

1. The 800 ms budget in `ops/load.js` fails locally by design: it encodes the
   objective, not today's result. Do not relax it to make a run green.
2. A Vercel deployment runs many instances and caches at the edge, so this number
   is a floor for the app code rather than a prediction of production. It has not
   been re-run against a deployed preview; that is the honest gap.

## What would move it

- Fewer sequential database round trips per page (each costs ~232 ms, see
  `docs/slo.md`). The search page issues five.
- Smaller home payload (246 KB uncompressed, all cities rendered in one response).

## Preview run (Sprint 9, S9-3)

Same script against the Vercel preview of `sprint9`
(`https://indian-food-recommends-3kxed4vg4.vercel.app`), k6 0.55.0. Previews sit behind
Vercel deployment protection, so the run passes an automation bypass secret. The secret was
created for this run and revoked afterwards.

```bash
BASE=https://<preview-host> BYPASS=<automation bypass secret> k6 run ops/load.js
```

The load client is in Canada (requests land on the `yul1` edge, TCP connect ≈ 5 ms). Functions
run in `sin1` next to the Neon database (`vercel.json`).

| Metric                  | Value                        |
| ----------------------- | ---------------------------- |
| Requests                | 1026 in 1 m 46 s (9.7/s)     |
| Checks passed           | 2052/2052 (100%)             |
| `http_req_failed`       | 0.00%                        |
| `http_req_duration` p50 | 780 ms                       |
| `http_req_duration` p95 | **1.12 s** (budget 800 ms)   |
| `http_req_waiting` p95  | 287 ms                       |
| Data received           | 14 MB (≈ 14 KB per page, br) |

Per path, an earlier run of the same profile (p50 / p95 total; first byte p95 stayed 290-303 ms on
every path): home 950 / 1180 ms, city 951 / 1153 ms, dish 864 / 1023 ms, place 924 / 1020 ms,
search 725 / 962 ms.

### Reading it

- The first run sent no `Accept-Encoding`, so k6 downloaded 131 MB of uncompressed HTML.
  Browsers always ask for compression. `ops/load.js` now sends `br, gzip`.
- With `cacheComponents` the edge answers with the cached shell (`x-vercel-cache: HIT`), then
  streams the dynamic part from the `sin1` function. Time to first byte is flat at ~256 ms; the
  remaining 0.5-0.8 s is that stream crossing Montreal to Singapore.
- Zero errors at 10 users, so this run shows no capacity problem. The p95 miss comes from client
  distance, which this run cannot separate from app time. Not measured: a client in India,
  which is where users are.
